# rok-db 0.4 proposal: Rust code from `.sql` files

- Status: **Draft**, waiting on maintainer decisions (see [Open questions](#open-questions))
- Target release: 0.4.0
- Becomes RFC 0005 (`docs/rfcs/0005-sql-codegen.md`) once accepted
- Related: [RFC 0002](rfcs/0002-cli.md) (CLI), which generates models from a *live*
  database. This proposal generates them from *SQL files*, and both share one generator.

## Summary

Write the schema and the queries in plain SQL, one file per table or aggregate, and let
rok-db turn them into Rust:

```text
db/user.sql                  ->  src/generated/db/user.rs    models + typed queries
db/post.sql                  ->  src/generated/db/post.rs
(all files, dependency order) -> src/generated/db/up.rs      apply migrations
                             ->  src/generated/db/down.rs    revert migrations
                             ->  src/generated/db/mod.rs     module tree
```

Each `<name>.sql` file becomes `<name>.rs`, with the same name. The schema statements
(`CREATE TABLE`, `CREATE TYPE ... AS ENUM`, indexes, constraints) become `#[derive(Model)]`
structs and migrations. Annotated queries (`-- name: find_by_email :one`) become typed async
functions. The generated code uses the normal rok-db API, so the query builder, joins,
relations, caching, tenancy and hooks all keep working.

## Motivation

- **SQL-first teams** already keep the schema in `.sql` files and review it as SQL. Today they
  must also write each model by hand and keep it in sync, which drifts.
- **Hand-written SQL** for reports and complex updates goes through `raw(..)` with untyped
  parameters and manual row structs. The types are only checked at runtime.
- **Migrations** need a separate tool (`sqlx-cli`) and still don't connect to the models.

The `.sql` file becomes the single source of truth, and generation plus a `--check` step in
CI keep the Rust side in sync.

## Conventions

### Directory layout

```text
my-app/
  db/                          # input: hand-written SQL (configurable)
    user.sql
    post.sql
    _types.sql                 # leading `_`: shared types and extensions, no module
  src/
    generated/
      db/                      # output: generated Rust, committed, never edited
        mod.rs
        user.rs
        post.rs
        up.rs
        down.rs
        migrations/            # one file per schema change (phase 2)
          m0001_init.rs
          m0002_add_post_slug.rs
        rok-db-schema.json     # schema snapshot used to compute the next migration
  rok-db.toml                  # optional configuration
```

- **Default output is `src/generated/db/`**, so it is an ordinary module:
  `mod generated;` in `main.rs` or `lib.rs`, with `src/generated.rs` containing `pub mod db;`.
- **`generated/db/` at the project root** (outside `src/`) also works. Use
  `--out generated/db` and include it with `#[path = "../generated/db/mod.rs"] mod db;`.
  The default stays under `src/`, because Rust tools (rust-analyzer, `cargo fmt`, docs) handle
  files there without extra setup.
- Generated files are **committed**. Reviewers see the Rust next to the SQL change, builds
  need no database, and `rok-db gen sql --check` in CI fails when they are stale.

### Naming

| Input | Output | Rule |
|---|---|---|
| `db/user.sql` | `user.rs`, `pub mod user;` | file stem, snake_case |
| `db/user-profile.sql` | `user_profile.rs` | `-` and spaces become `_` |
| `db/type.sql` | `type_.rs` | Rust keywords get a trailing `_` |
| `db/_types.sql` | no module (types land in `types.rs`) | a leading `_` marks shared statements |
| `db/up.sql`, `down.sql`, `mod.sql` | error | reserved output names |
| `CREATE TABLE users` | `pub struct User` | PascalCase, singular |
| `CREATE TABLE app.blog_posts` | `pub struct BlogPost`, `#[rok(table = "app.blog_posts")]` | schema kept in the table name |
| `CREATE TYPE post_status AS ENUM` | `pub enum PostStatus` (`#[derive(DbEnum)]`) | in the module of the file that declares it |
| `-- name: find_by_email` | `pub async fn find_by_email(..)` | snake_case, must be unique per file |
| a query's custom row | `pub struct FindByEmailRow` | `<QueryName>Row` |

A file may hold several tables. The recommended practice is one table (or one aggregate,
such as `order` plus `order_item`) per file. Two files producing the same struct or module
name is an error that names both files.

Every generated file starts with a header that tools recognise:

```rust
// @generated by rok-db-codegen 0.4.0 from db/user.sql. Do not edit.
// Source hash: 3f9a1c... (rok-db gen sql --check verifies it)
```

## Example

### Input: `db/user.sql`

```sql
CREATE TYPE user_role AS ENUM ('admin', 'member');

-- A person who can sign in.
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    email       TEXT NOT NULL UNIQUE,
    name        TEXT,
    role        user_role NOT NULL DEFAULT 'member',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at  TIMESTAMPTZ
);

CREATE INDEX users_role_idx ON users (role);

-- name: find_by_email :one
SELECT * FROM users WHERE email = $1;

-- name: count_by_role :many
SELECT role, count(*) AS total FROM users GROUP BY role ORDER BY role;

-- name: promote :exec
UPDATE users SET role = 'admin' WHERE id = $1;
```

### Input: `db/post.sql`

```sql
CREATE TABLE posts (
    id         BIGSERIAL PRIMARY KEY,
    author_id  BIGINT NOT NULL REFERENCES users (id),
    title      TEXT NOT NULL,
    views      INT NOT NULL DEFAULT 0
);

-- name: top_for_author :many
SELECT * FROM posts WHERE author_id = $1 ORDER BY views DESC LIMIT $2;
```

### Output: `src/generated/db/user.rs`

```rust
// @generated by rok-db-codegen 0.4.0 from db/user.sql. Do not edit.
use rok_db::prelude::*;

#[derive(Debug, Clone, Copy, PartialEq, Eq, DbEnum)]
#[rok(type_name = "user_role")]
pub enum UserRole {
    Admin,
    Member,
}

/// A person who can sign in.
#[derive(Debug, Clone, PartialEq, Model)]
#[rok(table = "users", timestamps, soft_delete, has_many(posts = super::post::Post::AUTHOR_ID))]
pub struct User {
    #[rok(primary_key, generated)]
    pub id: i64,
    pub email: String,
    pub name: Option<String>,
    #[rok(generated)] // has a DEFAULT; set it explicitly with `create().set(..)`
    pub role: UserRole,
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub updated_at: chrono::DateTime<chrono::Utc>,
    pub deleted_at: Option<chrono::DateTime<chrono::Utc>>,
}

/// `-- name: find_by_email :one`
pub async fn find_by_email<'e>(
    db: impl Executor<'e>,
    email: &str,
) -> rok_db::Result<Option<User>> {
    rok_db::raw("SELECT * FROM users WHERE email = $1")
        .bind(email)
        .fetch_optional(db)
        .await
}

/// A row of [`count_by_role`].
#[derive(Debug, Clone, PartialEq, rok_db::FromRow)]
pub struct CountByRoleRow {
    pub role: UserRole,
    pub total: i64,
}

/// `-- name: count_by_role :many`
pub async fn count_by_role<'e>(db: impl Executor<'e>) -> rok_db::Result<Vec<CountByRoleRow>> {
    rok_db::raw("SELECT role, count(*) AS total FROM users GROUP BY role ORDER BY role")
        .fetch_all(db)
        .await
}

/// `-- name: promote :exec`. Returns the number of rows changed.
pub async fn promote<'e>(db: impl Executor<'e>, id: i64) -> rok_db::Result<u64> {
    rok_db::raw("UPDATE users SET role = 'admin' WHERE id = $1")
        .bind(id)
        .invalidates("users") // keeps memoized queries correct
        .execute(db)
        .await
}
```

`post.rs` follows the same pattern: `Post` gets
`#[rok(belongs_to(author = super::user::User))]` on `author_id` (the name comes from the
column without `_id`), and `top_for_author(db, author_id: i64, limit: i64)` returns
`Vec<Post>`.

### Output: `up.rs`, `down.rs` and `mod.rs`

```rust
// up.rs: @generated. Apply every pending migration, in order, each in a transaction.
pub async fn up(db: &rok_db::Db) -> rok_db::Result<()> {
    rok_db::codegen::run_up(db, super::migrations::ALL).await
}

// down.rs: @generated. Revert the most recent migration (or `steps` of them).
pub async fn down(db: &rok_db::Db, steps: usize) -> rok_db::Result<()> {
    rok_db::codegen::run_down(db, super::migrations::ALL, steps).await
}

// mod.rs: @generated
pub mod migrations;
pub mod post;
pub mod user;
mod down;
mod up;
pub use down::down;
pub use up::up;
```

Using it:

```rust
use crate::generated::db::{self, user, user::User};

db::up(&pool).await?;                                         // migrate on startup or in tests
let ann = user::find_by_email(&pool, "ann@example.com").await?; // typed SQL
let admins = User::filter(User::ROLE.eq(user::UserRole::Admin)) // the normal builder
    .order_by(User::EMAIL)
    .all(&pool)
    .await?;
```

## How it works

### Pipeline

```text
db/*.sql --parse--> statements --analyze--> schema IR --emit--> Rust (quote + prettyplease)
                                    |                     \--> migrations (diff vs snapshot)
                                    \--check--> PostgreSQL (types of query params and columns)
```

1. **Parse** each file with `sqlparser` (PostgreSQL dialect). Comments directly above a
   statement are kept: `-- name:` annotations, `-- rok:` directives, and doc comments.
2. **Analyze** into a schema IR: tables, columns, keys, foreign keys, enums, indexes and
   queries. The same IR is what RFC 0002 builds from a live database, so both front ends share
   one Rust emitter.
3. **Check queries against PostgreSQL.** The generator creates a temporary database (the same
   mechanism as `TestDb`), applies the schema, and `PREPARE`s every query. PostgreSQL then
   reports the exact parameter types, result columns and nullability. Parsing SQL alone can't
   type expressions such as `count(*)`, `coalesce(..)` or `$1::date`. The results are cached
   in `src/generated/db/rok-db-queries.json`, so later runs and CI work **offline** (as in sqlx's
   offline mode). Only a changed query needs a database.
4. **Emit** formatted Rust and the header with the source hash.

### Schema to model mapping

This reuses the mapping table from RFC 0002, applied to SQL instead of the catalog:

| SQL | Rust |
|---|---|
| `BIGINT`/`BIGSERIAL`, `INT`/`SERIAL`, `SMALLINT`, `REAL`, `DOUBLE PRECISION`, `BOOLEAN` | `i64`, `i32`, `i16`, `f32`, `f64`, `bool` |
| `TEXT`, `VARCHAR(n)`, `CHAR(n)`, `CITEXT` | `String` (`VARCHAR(n)` adds `#[rok(validate(length(max = n)))]`) |
| `BYTEA` | `Vec<u8>` |
| `UUID` | `uuid::Uuid` (needs the `uuid` feature) |
| `TIMESTAMPTZ`, `TIMESTAMP`, `DATE`, `TIME` | `chrono` types (needs `chrono`) |
| `JSON`, `JSONB` | `serde_json::Value` (needs `json`) |
| `T[]` | `Vec<T>` |
| enum type | `#[derive(DbEnum)]` enum |
| no `NOT NULL` | `Option<T>` |
| `PRIMARY KEY` on one or several columns | `#[rok(primary_key)]` |
| `SERIAL`, identity, `DEFAULT ...`, `GENERATED ALWAYS AS (...)` | `#[rok(generated)]` |
| `created_at` + `updated_at` | `timestamps` |
| `deleted_at` | `soft_delete` |
| integer `version` | `#[rok(version)]` |
| `REFERENCES` | `belongs_to` on the child, `has_many` (or `has_one` when the column is `UNIQUE`) on the parent |
| `-- comment` above a table or column, or `COMMENT ON` | `///` doc comment |

When a type needs a rok-db feature that is off, generation fails with the feature to enable.
`rok-db.toml` overrides any mapping:

```toml
[codegen]
input = "db"
output = "src/generated/db"
derives = ["serde::Serialize", "serde::Deserialize"]   # added to every model and row

[codegen.types]
"numeric" = "rust_decimal::Decimal"

[codegen.tables.users]
struct = "Account"                 # instead of `User`
tenant = "org_id"                  # mark the tenant column
```

### Queries (data manipulation)

The annotation syntax follows [sqlc](https://sqlc.dev), so it is familiar and editors
highlight it as SQL:

| Annotation | Returns |
|---|---|
| `-- name: x :one` | `Result<Option<T>>` |
| `-- name: x :one!` | `Result<T>` (`Error::NotFound` when there is no row) |
| `-- name: x :many` | `Result<Vec<T>>` |
| `-- name: x :stream` | `BoxStream<'e, Result<T>>` |
| `-- name: x :exec` | `Result<u64>` (rows affected) |

- **Row type:** when the query returns exactly a table's columns (`SELECT *`, or
  `RETURNING *`), it reuses that model. Otherwise it gets a generated `<Name>Row` with
  `FromRow`.
- **Parameter names** come from what each `$n` is compared with (`email = $1` becomes
  `email: &str`). Use `-- param: $2 limit` to name one, or named parameters
  (`WHERE email = :email`), which are rewritten to `$n`.
- **Cache invalidation:** `INSERT`, `UPDATE` and `DELETE` queries call `.invalidates(..)` with
  the tables they write, so memoized queries stay correct.
- **Safety:** queries are static strings with bound parameters. There is no string
  interpolation, so they are not open to SQL injection.
- **Tenancy and soft deletes** are *not* applied automatically to hand-written SQL: the SQL
  runs exactly as written. For tables with a `tenant` column, the generator **warns** when a
  query doesn't filter on it (`--strict` makes this an error), and it does the same for
  `deleted_at` on soft-delete tables. Use the query builder when you want those scopes
  automatically.

### Migrations (`up.rs` and `down.rs`)

The `.sql` files describe the **desired** schema. Migrations are the steps that get a
database from one version to the next:

- **Phase 1 (bootstrap):** `m0001_init.rs` holds the full schema, with tables ordered by
  foreign keys. Cycles are split into `CREATE TABLE` followed by
  `ALTER TABLE ... ADD CONSTRAINT`. Its `down` drops everything in reverse order.
- **Phase 2 (diff):** after a change to `db/*.sql`, `rok-db gen sql --migration add_post_slug`
  compares the new IR with `rok-db-schema.json` and writes `m0002_add_post_slug.rs` with `up`
  (for example `ALTER TABLE posts ADD COLUMN slug TEXT`) and the matching `down`.
- **Destructive steps** (dropping a column, narrowing a type, adding `NOT NULL` without a
  default) stop generation and need `--allow-destructive`, or a hand-written step in a
  `-- rok:migration` block.
- `up` applies pending migrations in order, one transaction each. It records them in a
  `_rok_db_migrations` table (version, name, checksum) and refuses to run when an applied
  migration's checksum changed.
- `down(db, steps)` reverts the latest `steps` migrations.
- Hand-written statements the generator can't reverse, such as functions and triggers, need a
  `-- rok:down` block next to them:

```sql
CREATE FUNCTION touch_updated_at() RETURNS trigger ... ;
-- rok:down
DROP FUNCTION touch_updated_at();
```

- **Interop:** `rok-db gen sql --emit-sql migrations/` also writes plain
  `<version>_<name>.up.sql` / `.down.sql` files, so `sqlx-cli` and the existing
  `Db::migrate(dir)` keep working for teams that run migrations outside the app.

### Ways to run the generator

| Entry point | Use |
|---|---|
| `rok-db gen sql` (CLI from RFC 0002) | Default: writes the committed files. `--check` for CI, `--migration <name>` for a new step |
| `rok_db_codegen::Builder` in `build.rs` | Writes to `OUT_DIR` and is used with `include!`. No committed files, but no review diff either; needs the offline query cache |
| `cargo test` with the `testing` feature | `TestDb` can run `generated::db::up` so every test starts from the real schema |

### Crates

- New `crates/rok-db-codegen` (library). It depends on `sqlparser`, `quote`,
  `prettyplease`, `serde_json` and `sqlx` (only to check queries). Applications don't depend
  on it, so it doesn't affect their build times.
- The CLI from RFC 0002 (`rok-db-cli`) calls it.
- `rok-db` gains a small `codegen` module (behind a `codegen-runtime` feature): the migration
  runner (`run_up`, `run_down`, the `Migration` type) that generated code calls. The generated
  code itself only uses public rok-db APIs.

## Testing plan

- **Golden tests:** each fixture directory (`tests/codegen/<case>/db/*.sql`) has its expected
  output committed next to it. A test regenerates the output and compares it byte for byte.
- **Compile tests:** the generated output of every fixture is compiled as a crate in CI.
- **Database tests:** run `up`, the generated queries, then `down`, against PostgreSQL 14 and
  18. Also apply migration `N`, then `N+1`, and compare with a fresh `up` of the full schema
  (the two must produce the same catalog).
- **Error tests:** reserved names, name collisions, foreign-key cycles, unknown types, missing
  features, destructive diffs, and a stale `--check`.

## Phases

| Phase | Scope | Ships in |
|---|---|---|
| 1 | Models and enums from `CREATE TABLE` / `CREATE TYPE`; `mod.rs`; bootstrap `up` / `down`; `--check` | 0.4.0 |
| 2 | Annotated queries with PostgreSQL-checked types and the offline cache | 0.4.0 |
| 3 | Schema snapshots and diff migrations, destructive-change guard, `--emit-sql` | 0.4.x |
| 4 | Views as read-only models, `COMMENT ON`, partitioned tables, `build.rs` mode | 0.5 |

## Also proposed for 0.4

These come from the limitations review and are independent of code generation. Each gets its
own RFC:

1. **Many-to-many relations:** `#[rok(belongs_to_many(tags = PostTag))]` with `attach`,
   `detach`, `sync` and eager loading. The SQL generator would detect pivot tables (two foreign
   keys plus a composite primary key) and emit these attributes.
2. **Eager loading through joins:** `Post::query().with(Post::AUTHOR)` in one query.
3. **Async hooks and `after_commit`**, for side effects such as sending email that must only
   run when the transaction commits.
4. **Self-joins with aliases** (`User::alias::<Manager>()`), the last open item from RFC
   0001.

## Drawbacks

- **A second way to define models** (SQL files next to derives). Mixing them is supported:
  the generated models are ordinary derives. The docs should still recommend one style per
  project.
- **Exact query types need PostgreSQL** at generation time, at least once per changed query.
  The offline cache and the committed output keep builds and CI database-free.
- **Diff migrations are hard.** Renames look like a drop plus an add. The generator therefore
  asks (`--rename users.name=full_name`) instead of guessing, and refuses destructive steps by
  default.
- **More code to maintain:** a parser front end, the emitter, the diff engine and golden tests.

## Alternatives

- **Introspection only (RFC 0002 as written):** simpler, but it needs a live database, and the
  SQL files stop being the source of truth.
- **A proc macro, `rok_db::include_sql!("db/user.sql")`:** nothing to commit, but it hides the
  code, slows builds, makes errors harder to read, and needs the query cache at compile time.
  It could be added later on top of the same library.
- **Only typed queries (like `sqlx::query!`), no models:** loses the query builder, joins and
  relations for the same tables.

## Prior art

sqlc (Go and Kotlin: annotations and typed queries), sqlx (`query!` and offline mode),
Cornucopia and Clorinde (Rust: typed queries from `.sql` files), Prisma and Atlas (declarative
schema with diff migrations), and SeaORM and Diesel (`print-schema` / entity generation).

## Compatibility

Additive. It adds new crates, an optional runtime feature, and new generated files in the
user's project. Existing models, `Db::migrate` and `sqlx-cli` migrations keep working.

## Open questions

Each has a recommended answer.

1. **Default output directory:** `src/generated/db/` (recommended: a normal module) or
   `generated/db/` at the root with `#[path]`?
2. **Committed files or `build.rs`:** committed files plus `--check` in CI (recommended), or
   generated at build time?
3. **Query annotations:** sqlc-style `-- name: x :one` (recommended, familiar), or a
   rok-specific syntax?
4. **Migration model:** declarative files plus generated diff migrations (recommended), or
   hand-written numbered `.sql` migrations with only models generated?
5. **Tenancy in hand-written SQL:** warn by default and fail with `--strict` (recommended), or
   always fail?
6. **Order of work:** ship phases 1 and 2 in 0.4.0 and diff migrations in 0.4.x
   (recommended), or wait for all three?
