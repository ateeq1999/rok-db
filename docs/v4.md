# rok-db 0.4: Rust code from `.sql` files

- Status: **Accepted** and implemented (2026-10-09)
- Target release: 0.4.0
- Crates: `rok-db-codegen` (the `rok-db-gen` binary) and `rok_db::migration` in rok-db
- Related: [RFC 0002](rfcs/0002-cli.md) (CLI). RFC 0002 generates models from a *live*
  database; this generates them from *SQL files*.

## Summary

Write the schema and the queries in plain SQL, one file per table or aggregate. `rok-db-gen`
turns them into a Rust crate called `db-gen`:

```text
db/user.sql   ->  db-gen/src/user.rs        models, enums and typed queries
db/post.sql   ->  db-gen/src/post.rs
db/_types.sql ->  db-gen/src/types.rs       shared enums (leading `_`)
                  db-gen/src/up.rs          apply pending migrations
                  db-gen/src/down.rs        revert migrations
                  db-gen/src/migrations.rs  the migration list
                  db-gen/src/lib.rs
                  db-gen/migrations/0001_init.up.sql   (+ .down.sql)
                  db-gen/schema.json        schema snapshot for the next migration
                  db-gen/queries.json       query types checked by PostgreSQL
                  db-gen/Cargo.toml
```

`CREATE TABLE` / `CREATE TYPE ... AS ENUM` become `#[derive(Model)]` structs and `DbEnum`
enums. Annotated queries (`-- name: find_by_email :one`) become typed async functions.
Schema changes become migrations. The generated code uses the normal rok-db API, so the
query builder, joins, relations, caching, tenancy and hooks keep working.

## Decisions

| Question | Decision |
|---|---|
| Output location | A separate crate, `db-gen/`, with `db-gen/src/<file>.rs` per `.sql` file. Add it to the workspace and depend on it. |
| Committed or built | Committed. `rok-db-gen check` in CI fails when the files are stale. Builds need no database. |
| Query annotations | sqlc style: `-- name: <function> <:one, :one!, :many, :stream or :exec>`. |
| Migrations | Generated by comparing the `.sql` files with the snapshot of the last migration. |
| Tenancy in hand-written SQL | A warning when a query on a tenant table doesn't filter on the tenant column, and the same for soft-delete tables. `--strict` turns these into errors. |
| Order of work | Models, queries and migrations shipped together. |

## Using it

```sh
cargo install rok-db-codegen               # the `rok-db-gen` binary
export DATABASE_URL=postgres://localhost/postgres   # only needed when queries change
rok-db-gen generate                        # first run: db-gen/ with migration 0001_init
# ...edit db/*.sql...
rok-db-gen generate --migration add_slug   # writes 0002_add_slug and regenerates
rok-db-gen check                           # in CI
```

```toml
# Cargo.toml of your app
[workspace]
members = [".", "db-gen"]

[dependencies]
db-gen = { path = "db-gen" }
```

```rust
db_gen::up(&db).await?;                                    // apply pending migrations
let ann = db_gen::user::find_by_email(&db, "ann@example.com").await?;
let admins = db_gen::user::User::filter(db_gen::user::User::ROLE.eq(UserRole::Admin))
    .all(&db)
    .await?;
```

Settings live in an optional `rok-db.toml` at the project root:

```toml
[gen]
input = "db"
output = "db-gen"
crate_name = "db-gen"
rok_db_version = "0.4"     # or rok_db_path = "../rok-db/crates/rok-db"
strict = false
```

`examples/sqlgen` in this repository is a complete project, with its generated crate
committed.

## Naming

| Input | Output |
|---|---|
| `db/user.sql` | `src/user.rs`, `pub mod user` |
| `db/user-profile.sql` | `src/user_profile.rs` |
| `db/_types.sql` (leading `_`) | its enums go into `src/types.rs`; it may not hold queries |
| `db/up.sql`, `down.sql`, `lib.sql`, `migrations.sql`, `mod.sql`, `types.sql` | error: reserved |
| `CREATE TABLE users` | `pub struct User` with `#[rok(table = "users")]` |
| `CREATE TABLE app.blog_posts` | `pub struct BlogPost` with `#[rok(table = "app.blog_posts")]` |
| `CREATE TYPE user_role AS ENUM ('admin', 'in review')` | `pub enum UserRole { Admin, InReview }` with `#[rok(rename = "...")]` per variant |
| column `type` | `#[rok(column = "type")] pub type_` |
| `-- name: count_by_role :many` returning several columns | `pub struct CountByRoleRow` |

Two tables or enums with the same Rust name are an error that names both.

## Models

| SQL | Generated |
|---|---|
| `BIGSERIAL`, identity, `GENERATED ALWAYS AS (...)`, a primary key with a `DEFAULT` | `#[rok(generated)]`: PostgreSQL fills it in |
| other `DEFAULT`s | an ordinary field: `insert` writes what the struct holds |
| `created_at` + `updated_at` (timestamps) | `#[rok(timestamps)]` |
| nullable `deleted_at` | `#[rok(soft_delete)]` |
| integer `version` | `#[rok(version)]` |
| `-- rok:tenant` above a column | `#[rok(tenant)]` |
| `author_id BIGINT REFERENCES users` | `#[rok(belongs_to(author = crate::user::User))]`, and `has_many(posts = ...)` on `User` (`has_one` when the column is `UNIQUE`; `posts_by_author` when there are several keys to the same table) |
| `-- comment` above a table or column, or `COMMENT ON` | `///` doc comment |
| nullable column | `Option<T>` |

Types: `SMALLINT`/`INTEGER`/`BIGINT` (and serials), `REAL`, `DOUBLE PRECISION`, `BOOLEAN`,
`TEXT`/`VARCHAR`/`CHAR`/`NAME`, `BYTEA`, `UUID` (feature `uuid`), `TIMESTAMPTZ`/`TIMESTAMP`/`DATE`/`TIME`
(feature `chrono`), `JSON`/`JSONB` (feature `json`), one-dimensional arrays of those, and the
enums the files declare. The generated `Cargo.toml` enables the features the types need.

## Queries

| Annotation | Returns |
|---|---|
| `:one` | `Result<Option<T>>` |
| `:one!` | `Result<T>` (an error when there is no row) |
| `:many` | `Result<Vec<T>>` |
| `:stream` | `BoxStream<'e, Result<T>>` |
| `:exec` | `Result<u64>`, the rows affected |

- **Types come from PostgreSQL.** rok-db-gen creates a temporary database, applies the
  migrations, prepares each query and drops the database. Results are cached in
  `queries.json`, so only new or changed queries (or a schema change) need `DATABASE_URL`.
- **`T`** is the table's model when the query returns all of its columns (`SELECT *`,
  `RETURNING *`). It is the value itself for a single column, and a generated `<Name>Row`
  otherwise. Columns that PostgreSQL can't prove non-null become `Option`. Override with
  `AS "total!"` (never null) or `AS "total?"` (nullable).
- **Parameter names** come from what each `$n` is compared with:
  - `email = $1` and `lower(email) = lower($1)` become `email`;
  - `INSERT (a, b) VALUES ($1, $2)` names them after the columns;
  - `LIMIT` / `OFFSET` give `limit` and `offset`;
  - `x BETWEEN $1 AND $2` gives `x_from` and `x_to`;
  - `id = ANY($1)` gives `ids`.

  Anything else is `p<n>`. Name one explicitly with `-- param: $2 since`. `TEXT` parameters
  take `&str` and arrays take `&[T]`.
- **Cache:** writes call `.invalidates("table")`, so memoized queries stay correct.
- **Scopes:** hand-written SQL runs as written, so tenant and soft-delete scopes are not added.
  See the warnings above.

## Migrations

- The `.sql` files describe the desired schema. The first `generate` writes
  `0001_init`. After a change, `generate` stops and asks for `--migration <name>`, showing the
  first steps.
- Steps are ordered to work on a live database:
  1. removed views and other statements;
  2. extensions and enums;
  3. renames;
  4. dropped constraints and indexes;
  5. table and column changes;
  6. new constraints, then foreign keys once every table exists, so reference cycles work;
  7. new indexes;
  8. dropped tables and enums;
  9. new views and other statements.

  The down script undoes the steps in reverse.
- **Destructive steps** stop generation unless you pass `--allow-destructive`. These are:
  dropping a table, column or enum; changing a column type or the primary key; making a
  column `NOT NULL`; and adding a `NOT NULL` column without a `DEFAULT`.
- **Renames:** `--rename users=accounts` or `--rename users.name=full_name` turns a
  drop-and-add into `ALTER TABLE ... RENAME`.
- **Irreversible steps:** adding an enum value can't be undone in PostgreSQL. Such a
  migration has no `.down.sql`, and `down()` refuses to revert it.
- **Other statements:** functions, triggers, seed data and the like need their undo SQL in a
  `-- rok:down` block right after them. Extensions, views and `COMMENT ON` get one
  automatically.
- **Runtime:** `db_gen::up(&db)` / `db_gen::down(&db, steps)` call `rok_db::migration`:
  - one transaction per migration, holding an advisory lock;
  - applied migrations are recorded in `_rok_db_migrations` with a checksum;
  - it refuses to run when an applied migration was edited.

  The files use sqlx's `<version>_<name>.up.sql` naming, so `sqlx migrate` and
  `Db::migrate("db-gen/migrations")` also work, with their own history table.

## Formatting

Generated modules are marked `#[rustfmt::skip]` in `lib.rs`, so `cargo fmt` on the workspace
doesn't change them and `check` keeps passing.

## Limitations

- Queries can't contain `?`, because rok-db's `raw()` reads it as a placeholder. Use `$n`
  parameters and `jsonb_exists(...)` instead of the `?` operator.
- `NUMERIC`, intervals, network and range types have no rok-db column type yet.
- Removing or reordering enum values, and changing a `GENERATED` / identity column, need a
  hand-written migration.
- Describe the final schema with `CREATE` statements. `ALTER TABLE` in the `.sql` files is
  treated as an extra statement, not as part of the tables.
- Views are applied but don't become models.
- Relations are inferred only for single-column keys.

## Testing

- **Unit tests:** the statement splitter, naming, types, the parser, the migration differ,
  the emitters and parameter naming.
- **`examples/sqlgen`:** a golden test regenerates the example offline from `queries.json`
  and compares it with the committed files. A PostgreSQL test runs `up`, every generated
  query kind, the relations and `down`.
- **Workflow test:** a scratch project goes from `init` through enum and column changes, the
  destructive guard, a rename and a new table. Every migration is applied to PostgreSQL and
  the last two are reverted.
- **`rok_db::migration`:** apply, revert, edit detection, unknown versions, rollback of a
  failing migration, and irreversible migrations.

## Also proposed for 0.4

These are independent of code generation, and each needs its own RFC:

1. **Many-to-many relations:** `belongs_to_many` with `attach`, `detach` and `sync`. The
   generator would detect pivot tables.
2. **Eager loading through joins:** `Post::query().with(Post::AUTHOR)`.
3. **Async hooks and `after_commit`.**
4. **Self-joins with aliases.**
