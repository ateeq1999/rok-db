# Summary

Add `migrate status`, `migrate up` and `migrate down` commands to the existing
`rok-db-gen` binary, so migrations generated by `rok-db-gen` can be inspected, applied
and reverted from a terminal or a deploy script without writing a Rust program.

## What changed since the first draft

The first draft (2026-10-03) proposed a new `rok-db-cli` crate with a `rok-db` binary
for migrations (`add`, `run`, `revert`, `status`) and for generating models from a
live database. Version 0.4 shipped most of the motivation another way:

| First draft | Shipped in 0.4 |
|---|---|
| `rok-db gen models` from a live database | `rok-db-gen generate` from `.sql` files (`docs/v4.md`) |
| `migrate add` (hand-written files) | `rok-db-gen generate --migration <name>` writes the migration from a schema diff |
| `migrate run` / `revert` | `db_gen::up(&db)` / `db_gen::down(&db, n)` in Rust, over `rok_db::migration` |
| schema diffing (an open question) | done, with a destructive-change guard and `--rename` |

What is still missing is running migrations without code: checking what a database has
applied, and applying or undoing migrations from CI, a deploy step or a developer's
shell. Generating `.sql` files from an existing database (`pull`) remains useful and is
listed under Future possibilities.

# Motivation

- Today the only way to apply generated migrations is to call `db_gen::up(&db)` from a
  program. Teams that migrate as a deploy step (before the new version starts) have to
  write and ship a small binary for it.
- There is no way to see which migrations a database has applied, or whether its
  checksums still match, without querying `_rok_db_migrations` by hand.
- Reverting during development (`down` one step, edit, `generate`, `up`) needs a
  throwaway program.

# Guide-level explanation

```sh
export DATABASE_URL=postgres://localhost/app

rok-db-gen migrate status
#   version  name           state     checksum
#   1        init           applied   ok
#   2        add_post_slug  applied   ok
#   3        add_comments   pending
rok-db-gen migrate up                # applies 3; prints "applied 3 add_comments"
rok-db-gen migrate down              # reverts 3
rok-db-gen migrate down --steps 2    # reverts 3 and 2
```

The commands read the same `rok-db.toml` (or `--config`, `--output`) as `generate`, and
take their migrations from `<output>/migrations/*.sql`, the files the generated crate
embeds. They need `DATABASE_URL` (or `--database-url`).

`status` exits non-zero when an applied migration was edited (checksum mismatch) or the
database has a migration the files don't, so CI can catch drift.

# Reference-level explanation

- **Loading.** `<output>/migrations/NNNN_name.up.sql` and the matching `.down.sql` (empty
  when missing, as for `ALTER TYPE ... ADD VALUE`) become `rok_db::migration::Migration`
  values, version and name parsed from the file name. The contents are byte-for-byte what
  the generated crate embeds with `include_str!`, so checksums match those recorded by
  `db_gen::up` and the two can be mixed freely. Files that don't match the pattern are an
  error naming the file.
- **Running.** `up`, `down` and `status` call `rok_db::migration::apply`, `revert` and
  `applied`. Locking, one transaction per migration, checksum checks and refusal of
  unknown or out-of-order migrations come from there unchanged.
- **Output.** One line per migration applied or reverted; `status` prints a table. No
  colours, so the output works in CI logs.
- **Dependencies.** `rok-db-codegen` gains a normal dependency on `rok-db` (it already has
  sqlx and tokio). No new crate, no `clap`: the binary keeps its small hand-written
  argument parser.
- **Exit codes.** `0` on success, `1` on any error, and for `status`, `1` on drift.

# Drawbacks

- `rok-db-gen` becomes both a generator and a migration runner. The alternative is a
  second binary that reads the same configuration and files.
- The binary now connects to the target database (production, in a deploy step), not
  only to a throwaway one. Its output and error messages must never print the
  connection string (it carries the password); a test checks this.

# Rationale and alternatives

- **A separate `rok-db-cli` crate** (the first draft). Clearer naming, but a second
  install and a second configuration for files `rok-db-gen` already owns.
- **Generate a `migrate` binary inside the generated crate.** No separate install and
  migrations are compiled in, but it adds a `[[bin]]`, `tokio` and argument parsing to
  every generated crate, most of which only need `up()`.
- **Point users at `sqlx migrate`.** It can read the files, but records them in a
  different table (`_sqlx_migrations`) with different checksums, so the two runners
  would disagree about what is applied.

# Prior art

`sqlx migrate run|revert|info`, `diesel migration run|revert|list`, `sea-orm-cli migrate
up|down|status`, `prisma migrate deploy|status`, Rails `db:migrate`, `db:rollback`,
`db:migrate:status`.

# Compatibility

Additive: new subcommands. `generate` and `check` are unchanged. Migrations applied by
`db_gen::up` and by `rok-db-gen migrate up` are interchangeable.

# Unresolved questions

1. **Subcommands of `rok-db-gen`, or a new binary?** Recommended: subcommands of
   `rok-db-gen` (same configuration and files, nothing else to install).
2. **How far does `down` go by default?** Recommended: one migration; `--steps N` for
   more. No `--all`: reverting everything is rare and `--steps` with a large number does
   it explicitly.
3. **Should `up` take `--to <version>`?** Recommended: not now. Applying everything
   pending is what deploys do; partial application can come later if asked for.

# Decisions

Accepted by the maintainer on 2026-10-09:

1. Subcommands of `rok-db-gen`, not a new binary or crate.
2. `down` reverts one migration by default; `--steps N` for more; no `--all`.
3. No `up --to <version>` for now.

# Future possibilities

- `rok-db-gen pull`: write `CREATE TABLE` / `CREATE TYPE` `.sql` files from an existing
  database (introspecting `pg_catalog`), so adopting rok-db on a live schema is `pull`
  then `generate`. This reuses the whole 0.4 pipeline instead of generating models
  directly, and needs its own RFC.
- `migrate up --to <version>`, `migrate redo` (down then up), and shell completions.
- Seeding (`rok-db-gen seed`).
