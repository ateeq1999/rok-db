# Summary

Ship a `rok-db` command-line tool (crate `rok-db-cli`) that manages
migrations and generates rok-db models from an existing PostgreSQL schema.

# Motivation

- Adopting rok-db on an existing database means hand-writing one struct per
  table with the right Rust types, `#[rok(...)]` attributes and relations.
  That's tedious and error-prone (nullability, generated columns, keys).
- Migrations already work at runtime (`Db::migrate`, feature `migrate`), but
  creating, listing and reverting them needs a tool. Today that means
  installing `sqlx-cli` separately, which knows nothing about rok-db models.
- A generator that knows rok-db's conventions (timestamps, soft deletes,
  versions, tenants, relations, enums) removes most of the boilerplate.

# Guide-level explanation

```sh
cargo install rok-db-cli            # installs the `rok-db` binary

rok-db migrate add create_users      # migrations/20261003120000_create_users.sql (+ .down.sql with --reversible)
rok-db migrate run                   # apply pending migrations (DATABASE_URL or --database-url)
rok-db migrate revert                # revert the latest reversible migration
rok-db migrate status                # applied / pending, with checksums

rok-db gen models --out src/models   # one file per table + mod.rs
rok-db gen models --tables users,posts --schema public --dry-run
```

Generated code, for a `posts` table:

```rust
// @generated by rok-db gen models — edit freely; re-run with --force to overwrite.
use rok_db::prelude::*;

#[derive(Debug, Clone, PartialEq, Model)]
#[rok(table = "posts", timestamps, soft_delete)]
pub struct Post {
    #[rok(primary_key, generated)]
    pub id: i64,
    #[rok(belongs_to(author = super::user::User))]
    pub author_id: i64,
    pub title: String,
    pub body: Option<String>,
    pub tags: Vec<String>,
    pub status: super::enums::PostStatus,   // CREATE TYPE post_status AS ENUM (…) → #[derive(DbEnum)]
    pub created_at: chrono::DateTime<chrono::Utc>,
    pub updated_at: chrono::DateTime<chrono::Utc>,
    pub deleted_at: Option<chrono::DateTime<chrono::Utc>>,
}
```

# Reference-level explanation

## Crate and binary

- New workspace member `crates/rok-db-cli`, binary `rok-db`, built on `clap`
  (derive), `tokio`, `sqlx` (Postgres, migrate) and `prettyplease` for output
  formatting. It depends on `rok-db-core` only for shared naming helpers.
- Configuration, in order of precedence: flags, environment (`DATABASE_URL`),
  then an optional `rok-db.toml` (`database_url`, `migrations_dir`,
  `models_dir`, type overrides).

## Migrations

Thin wrappers over `sqlx::migrate::Migrator` so files stay compatible with
`sqlx-cli` and `Db::migrate`: timestamped names, optional `.up.sql` /
`.down.sql` pairs, checksum verification, and `status` output.

## Model generation

Introspection queries `information_schema` and `pg_catalog`:

| Schema fact | Generated |
|---|---|
| column type | Rust type (`int8` → `i64`, `text` → `String`, `timestamptz` → `DateTime<Utc>`, `uuid` → `Uuid`, `jsonb` → `serde_json::Value`, arrays → `Vec<T>`, …) |
| `NULL`able | `Option<T>` |
| primary key (one or several columns) | `#[rok(primary_key)]` |
| identity / serial / `DEFAULT` expression | `#[rok(generated)]` (configurable) |
| `created_at` / `updated_at` with defaults | `#[rok(timestamps)]` |
| `deleted_at` | `#[rok(soft_delete)]` |
| integer `version` | `#[rok(version)]` |
| foreign key | `#[rok(belongs_to(...))]` on the child, and `#[rok(has_many(...))]` on the parent |
| enum type | `#[derive(DbEnum)] #[rok(type_name = "…")]` in `enums.rs` |
| table name ≠ pluralised struct name | `#[rok(table = "…")]` |

Unknown types fall back to `String` with a `// TODO` comment, or to an
override from `rok-db.toml`:

```toml
[types]
"numeric" = "rust_decimal::Decimal"
"public.money" = "crate::Money"
```

Re-running doesn't overwrite existing files unless `--force` is given.
`--check` exits non-zero if the generated output would differ, for CI drift
detection.

# Drawbacks

- A new crate to maintain, with a larger dependency tree (`clap`,
  `prettyplease`). It's a separate binary crate, so library users don't pay
  for it.
- Introspection depends on catalog details that vary across PostgreSQL
  versions; it needs tests against every supported major version.

# Rationale and alternatives

- **Document `sqlx-cli` for migrations and skip generation**: no new code,
  but the main adoption pain (writing models) remains.
- **A build-script or macro that reads the schema at compile time**: no files
  to maintain, but builds would need database access, which hurts CI, offline
  builds and reproducibility. Generated source is reviewable and editable.

# Prior art

`sea-orm-cli generate entity`, `diesel print-schema`, Prisma introspection
(`prisma db pull`), and `sqlx-cli` for migrations.

# Compatibility

Additive: a new crate. Migration files stay compatible with `sqlx-cli`.

# Unresolved questions

1. Should `gen models` also emit `has_many`/`has_one` on parents (they can be
   wrong for one-to-one relations), or only `belongs_to`?
2. One file per table, or a single `models.rs`?
3. Should migrations be generated from model changes (schema diffing)? This
   proposal says no: it's much larger and belongs in its own RFC.

# Future possibilities

Schema diff to migration (`rok-db gen migration --from-models`), seeding
(`rok-db seed`), and shell completions.
